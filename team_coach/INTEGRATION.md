# Интеграция тренера с Open Hyper AI

Карта нужна для правки телеметрии и поведения ботов в локальном лобби. В режиме `shadow` тренер собирает материал для разбора. В режимах `observe`, `rules` и `model` он принимает типизированные команды для конкретных ботов. `observe` оставляет решения оператору, а `rules` и `model` также пересматривают план автоматически.

## Копии скриптов

- Исходник установленного Open Hyper AI находится в `steamapps\workshop\content\570\3246316298`. Эта карта проверена по сборке `0.7.41 - 2026/04/16` из `FuncLib/systems/version.lua`.
- Dota загружает подключённую копию из `steamapps\common\dota 2 beta\game\dota\scripts\vscripts\bots`, когда в локальном лобби выбран **Local Dev Script**. Установщик создаёт её из Workshop, добавляет Lua-адаптер и вносит правки в точки входа. Постоянные правки вносятся в [install.py](install.py) и [adapter.lua](adapter.lua), затем копия собирается заново.
- Для проверки сборки без установки в игру у [установщика](install.py) есть `--target ПУТЬ_К_ПАПКЕ_BOTS`. Родительская папка должна существовать. Для подготовки файлового канала при сборке без запуска сервера используй `python -X utf8 -m team_coach.install --target ПУТЬ_К_ПАПКЕ_BOTS --log-telemetry --file-commands`.

## Роли в локальной лиге

Выбранная позиция игрока исключается из пула союзных ботов. Драфт подбирает героев для остальных четырёх позиций, а Open Hyper AI использует этот состав для начальных линий и ролевых билдов. Для позиции 2 центр остаётся соло. Позиции 1 и 5 делят лёгкую линию, позиции 3 и 4 — сложную. Пик игрока остаётся свободным. При совпадении с запланированным пиком бот получает другого героя своей позиции.

Назначение касается стартовой расстановки и роли бота. Ганги, телепорты и помощь на соседних линиях продолжают работать. Настройка состава передаётся из локальной лиги отдельно от сервера тренера и действует при выключенном тренере.

| Когда отступить | `mode_retreat_generic.lua:GetDesire` и `GetDesireHelper`. Действие режима `BOT_MODE_RETREAT` выполняет движок. | `retreat` повышает положительную штатную оценку при угрозе. Он имеет приоритет над фармом и надбавкой к пушу для указанных ботов. В `model` отход назначает сессия, в `rules` — локальная политика после устойчивой изоляции или продолжения драки после потерь. |
| Где и когда собраться для драки | `mode_team_roam_generic.lua` получает краткосрочную оценку и действие из [fight_adapter.lua](fight_adapter.lua). | План задаёт цель, участников и общую фазу. Если бот теряет видимость, поддержку или безопасный путь, снова работает штатный режим. |

Хук рассчитан на Lua-касты по всему пулу. Покрытие каждого героя в живом матче ещё предстоит подтвердить. |

Lua повышает только положительную штатную оценку для выбранного бота. Надбавка ограничена `0.14`. У фарма, пуша и защиты потолок ниже `BOT_MODE_DESIRE_HIGH`, отход имеет собственный потолок. Приоритет и безопасность ещё раз проверяются в самой игре перед применением.

## Команды тренера

Базовый адрес API по умолчанию — `http://127.0.0.1:32125`. `GET /health` проверяет сервер, `GET /status` показывает состояние матча и подтверждения от ботов, `GET /commands` возвращает схему `catalog` из [commands.py](commands.py) и список `active` с ID действующих команд и плана.

### Тактические цепочки

Команда `python -X utf8 -m team_coach.control --port 32126 playbook` показывает схему и состояние цепочек. Добавь путь к JSON-файлу или `-` для ввода через stdin. Формат содержит `window_s` и до трёх объектов в `chains`. У каждого объекта есть `id`, `wait_s`, `start`, `on_success` и `on_failure`. Шаг содержит `action`, `target`, `bot_ids`, `ttl_s`, `reason` и поле `opener`. Для шага без назначенной способности укажи `opener: null`. Необязательную ветку можно целиком задать как `null`.

Например, первая группа собирается на `pickoff` видимого героя с `opener` равным `{"bot_id":8,"ability":"axe_berserkers_call"}` и имеет запасной `retreat`, а вторая группа одновременно держит `push` другой линии. Наблюдаемая гибель цели открывает `on_success`. Потеря обзора, недоступность инициатора, распад состава или истечение `wait_s` открывают `on_failure`. Следующий шаг ещё раз проходит проверку карты и состава. Для `push` успехом считается смена вышки, для `defend` — уход угрозы при стоящей вышке. Одновременно действуют один план файта, один план линии и отдельные приказы на отход или Рошана.

Контроллер проверяет условия на каждом свежем снимке. При активном файте с назначенной способностью его участники публикуют сводки раз в одну игровую секунду. Инициатор применяет поддерживаемую способность в радиусе каста при подходящей цели и поддержке группы. `opener_applied` означает, что после выданного приказа способность ушла на кулдаун. Попадание проверяется по дальнейшему состоянию. Переходы и причины видны в `playbook_step`. При изменении запасной ветки сохраняй `id` цепочки и текущий шаг. Пустой `chains` отменяет приказы этой подборки.

| Режим запуска | Ручные команды | Автоматические решения |
| --- | --- | --- |
| `--mode shadow` | Операции чтения | Сводки и наблюдения для журнала |
| `--mode observe` | Отправка и отмена команд и плана | — |
| `--mode rules` | Отправка и отмена команд и плана | Планы файтов, пуша или защиты и короткий отход при подтверждённой опасности |
| `--mode model` | Отправка и отмена команд и плана | Постоянная сессия напрямую принимает стратегические и тактические решения каждые 15 секунд или по событию |

Для автоматических файтов в локальной лиге запусти тренера с файловыми ответами перед новым матчем.

```powershell
$dotaLog = 'C:\Program Files (x86)\Steam\steamapps\common\dota 2 beta\game\dota\offline_league.log'
python -X utf8 -m team_coach --install --mode rules --dota-log $dotaLog
```

`--dota-log` в `shadow` включает чтение сводок. В режимах управления он также включает файловую доставку ответов. С `--mode observe` решения задаются вручную. Для перехода между конфигурацией наблюдения и управления повтори запуск с `--install` при свободном порте. Если в клиенте уже загружена карта лиги, перезапусти Dota после установки, чтобы обновлённые Lua-скрипты подхватились при загрузке карты.

Параметры `--team radiant|dire` и `--port` должны совпадать с настройкой установленного адаптера. `--log ПУТЬ` задаёт файл событий. `--decision-interval` задаёт период пересмотра плана при макро 100% в пределах 2–20 игровых секунд, по умолчанию 2 секунды. Для `model` есть параметры `--max-calls`, `--cooldown`, `--model`, `--effort` и `--model-timeout`. Полный список показывает `python -m team_coach --help`.

### Действия и условия

| Команда | Цель | Срок, игровые секунды | Когда сервер принимает команду |
| --- | --- | --- | --- |
| `push` | `{"kind":"lane","lane":"top"}`, также `mid` и `bot` | 15–60 | Есть вражеская вышка, союзная волна и достаточно союзников рядом. База вне угрозы. |
| `defend` | `{"kind":"lane","lane":"top"}`, также `mid` и `bot` | 15–60 | Противники рядом с союзной вышкой. |
| `farm` | `{"kind":"self"}` | 10–30 | У бота от 65% HP, поблизости нет противников, входящего урона и угрозы базе. У бота положительная оценка фарма, нет боя, отхода, Рошана или команды на линию. |
| `roshan` | `{"kind":"roshan"}` | 10–30 | Рошан виден или доступен по оценке. Есть минимум два здоровых бота с положительной штатной оценкой и без врагов рядом. |
| `retreat` | `{"kind":"self"}` | 3–15 | У бота положительная оценка отхода. Бот получает урон либо имеет не более 55% HP при перевесе противников рядом минимум на два героя. |
| `hold_ultimate` | `{"kind":"ability","name":"enigma_black_hole"}` или имя любой изученной активной ульты из `context.allies[].ultimates` | 2–10 | У выбранного бота способность изучена, не активна и её кулдаун не больше 0,5 с. Команда блокирует подходящий Lua-каст до выдачи приказа. |
| `pickoff` | `{"kind":"enemy","id":5}` | 6–30 | Видна изолированная уязвимая цель. Приоритет у архетипов саппортов и у героев с низкими ресурсами. Рядом два или три готовых бота. |
| `gank` | `{"kind":"enemy","id":5}` | 6–30 | С четвёртой минуты у команды соперника в двухстороннем запуске. Видимого керри или мидера можно перехватить вне вышек. Для разогнавшейся цели или одного видимого подкрепления собираются три бота. |
| `flank` | `{"kind":"enemy","id":5}` | 6–30 | Три доступных бота. Ведущий сохраняет фронт. Другие ищут видимый проход сбоку. Вход требует подтверждения позиций. |
| `bait` | `{"kind":"enemy","id":5}` | 6–30 | Видна готовая BKB или готовый командный ультимейт. Здоровый ведущий коротко давит на цель. Союзники остаются рядом. После реакции план предусматривает отход и проверку окна для входа. |
| `counterattack` | `{"kind":"enemy","id":5}` | 6–30 | Цель видна после окончания BKB или после наблюдаемого перехода ультимейта на кулдаун. Минимум два готовых бота в радиусе входа. |

Для `push` и `defend` список допустимых линий и ботов приходит в `context.choices`. Боты в этом списке живы, имеют от 65% HP и не находятся в режиме отхода. В любой момент действует один план линии. `retreat` и `hold_ultimate` могут действовать вместе с ним. Для одного бота команды `farm` и `retreat` взаимоисключающие, а `hold_ultimate` задаётся отдельно.

### План файта

В `fight_choices` видны доступные тактики, цели и участники. В `fight` возвращается текущий план. Фазы `stage`, `probe`, `reset` и `commit` означают сбор, пробное давление, отход и вход. Сбор проверяет готовность ведущего и ещё одного бота. Для обхода план дополнительно проверяет угол между ними. При потере обзора, усилении противника, приоритетной защите или истечении срока план заканчивается, и боты возвращаются к штатным решениям.

На подготовке и отходе у здорового бота в безопасной позиции план может придержать его ультимейт. При входе, уроне или срыве плана резерв снимается. Ведущий в `bait` сохраняет возможность использовать ультимейт для выхода. Ручное удержание живёт по своему сроку.

`fight_ready` показывает ботов, подтвердивших позицию. `fight_applied` показывает ботов, выдавших тактический приказ на текущей фазе. Подтверждение приказа к атаке не измеряет попадание или итог. После гибели цели в фазе входа `rules` и `model` могут раньше пересмотреть возможность пуша по волне и состоянию вышек.

В двухстороннем запуске тренер соперника может начать ганг автоматически и в `observe`. Выбор опирается на текущую видимость команды, позиции, уровни и счёт героев. Ближайшего бота поддерживают саппорты, керри до десятой минуты остаётся на своём маршруте. Для входа нужны подтверждения всех участников. Нулевая настройка макро отключает автоматический ганг. После попытки цель получает паузу в 35 игровых секунд для повторного автоматического ганга.

При потере участника контроллер соперника может пересобрать группу по свежему обзору, отвести раненого или перенести давление на другую линию под подходящую волну. План без реакции ботов пересматривается через шесть игровых секунд. Для защиты соперник выбирает доступных по реальной дистанции или TP героев. Lua может подвести их за свою вышку, если штатная оценка защиты равна нулю. Тайминг кастов, текущая драка и опасная точка высадки могут остановить ротацию. Журнал пишет причину снятия плана, замену в `pressure_replanned` и подтверждение выданного приказа на ротацию в `bot_applied`.

При входе штатные скрипты способностей получают общую цель на время одного решения. Против разогнавшейся цели Doom и Beastmaster могут открыть окно своей ультой, а Lina, Lion и Sniper могут добить её при достаточном уроне. Применение проверяет видимость, готовность, дистанцию и защитные эффекты. Активные касты и очередь комбинации имеют приоритет перед движением по плану.

Проверка BKB использует два соседних видимых состояния. Для окна по ультимейту нужна наблюдаемая смена готовности на кулдаун. Активная анимация может начать отход, но сама по себе не открывает повторный вход. Lua-адаптер локальной лиги передаёт видимый модификатор BKB и доступный текущий каст. Готовность BKB и кулдауны врага принимаются только при наличии этих полей в телеметрии. Метка саппорта берётся из архетипа Open Hyper AI и служит подсказкой при равной доступности целей.

Боковой подход и отказ от входа без позиции опираются на разборы Team Spirit, а повторный вход после BKB — на эпизод финала DreamLeague S27. ### Два тренера и коллы игрока

Двухсторонний запуск использует одну установленную копию Open Hyper AI. Выбери **Local Host** и **Local Dev Script** для Radiant и Dire. Параметр `--team` обозначает сторону игрока. Для локальной лиги с консольной телеметрией используй:

```powershell
$dotaLog = 'C:\Program Files (x86)\Steam\steamapps\common\dota 2 beta\game\dota\offline_league.log'
python -X utf8 -m team_coach --both --install --team radiant --dota-log $dotaLog
```

У команды игрока по умолчанию порт `32125`, у соперников `32126`. Запуск создаёт две постоянные сессии и выводит их ID и пути к журналам. В `model` сессии работают параллельно: каждые 15 игровых секунд или по значимому событию получают только сведения своей команды и напрямую выдают стратегические и тактические приказы. Пока ответ выполняется, продолжаются текущие приказы и штатное управление героев; правила не выбирают альтернативный план. У соперника отдельная инструкция на максимальное давление. Настройки лиги передаются в `map.tuning` — `bot_difficulty`, `micro`, `macro`, `coach`. Отсутствующие поля получают максимум. Для управления из внешних сессий через API используй `--mode observe --opponent-mode observe`. В командном чате выбирается единственный человек на стороне игрока. Если их несколько, укажи `--caller-id` с ID своего слота.

Сессия возвращает `orders`, `cancel_ids`, `reason` и `playbook`. Каждый приказ содержит `action`, `target`, `bot_ids`, `ttl_s`, `reason` из каталога команд. `playbook: null` сохраняет текущие цепочки. Сервер перепроверяет доступность по текущей телеметрии и сразу публикует допустимые приказы с `source=model`. Команды человека имеют приоритет. В `GET /status` доступны `coach_session` и `last_model_result`, в журнале — события `coach_requested`, `coach_replied`, `coach_orders` и ошибки. Параметр `--cooldown` задаёт период сессии. `--decision-interval` задаёт период для режима `rules`. Новый матч создаёт новую историю, восстановление транспорта продолжает текущую сессию.

Свежий пинг у вышки или ямы фиксируется как подсказка. В контексте соперника поле `player_call` отсутствует. [API чата и пингов](https://github.com/forest0xia/dota2bot-OpenHyperAI/blob/main/docs/BOT_API_REFERENCE.md#callbacks)
3. **Разобрать и проверить намерение.** Тренер хранит автора, игровое время, цель и срок колла. Ясный колл запускает внеочередной пересмотр по локальным правилам. Приоритет сохраняется у срочного отхода и защиты базы. На пуш проверяются волна, вышка и достижимость для союзников. Для Рошана проверяются текущая яма, готовность команды, видимая угроза и источник сведений о самом Рошане. Видимая цель и оценка по таймеру записываются отдельно.
4. **Передача штатному режиму.** Пуш использует `push`. Для `roshan` нужны минимум два живых здоровых бота с положительной штатной оценкой и сведения о возможной доступности Рошана. Команда поднимает оценку существующего режима. Его `Think` собирает союзников и атакует видимого Рошана. В журнале сохраняются распознанный колл, принятие или истечение срока, подтверждение от ботов и отмена при смене обстановки.

В локальном матче лиги оба тренера подтвердили связь с ботами. Союзный тренер получил коллы на пуш, Рошана и отмену, в журнале соперников эти коллы отсутствовали. Боты обеих сторон подтвердили защиту мида и сбор перед файтом. Бот Dire подтвердил отход. Zeus и Witch Doctor подтвердили переключение в режим Рошана по команде API.

Первую проверку удобно провести в режиме наблюдения. Записать коллы обеих сторон, дубликат пинга и колл без подходящих условий. Затем в режиме управления проверить, что союзники реагируют один раз, чужой тренер и его журнал не получают команду, а отмена и смена матча снимают план.

### Проверка удержания ультимейтов

Адаптер берёт имя способности из актуального списка изученных активных ультимейтов бота, а Lua перепроверяет принадлежность способности герою. Общий хук охватывает обычные, поставленные в очередь и добавленные в очередь спереди Lua-приказы на применение способности. Уже начатый каст и включённый переключаемый ультимейт сохраняют своё состояние. Приказы движка вне этих Lua-вызовов находятся вне проверенного контура.

В тестах сервиса проверено принятие команд для Laguna Blade и Ravage из актуальной телеметрии. Для живой проверки нужны разные формы каста, в том числе Ravage без цели, Black Hole на точку с подготовкой Blink или BKB и украденная способность Rubick. Запись `command_applied` подтверждает срабатывание хука. Для автоматического резерва дополнительно проверь, что после входа в драку или срыва плана `SkillsComplement` снова может выдать штатный приказ. При расширении автоматических правил учитывай роль ультимейта в плане, например инициацию или спасение союзника. [Адаптер](adapter.lua) · [Тесты](../tests/test_team_coach.py)

### Командная строка

Запускай из корня проекта. Каталог открывается без запущенной Dota и без сервера тренера.

```powershell
python -X utf8 -m team_coach.control list
python -X utf8 -m team_coach.control list --active
python -X utf8 -m team_coach.control status
```

`list --active` показывает каталог и действующие команды сервера. `status` показывает свежую сводку матча, ID союзников и доступные варианты по линиям. Примеры используют условные ID. Для отправки возьми актуальные значения из сводки.

```powershell
python -X utf8 -m team_coach.control send retreat --bots 2 --ttl 8 --reason 'Бот принимает урон.'
python -X utf8 -m team_coach.control send defend --target mid --bots 2 3 --ttl 25 --reason 'Защита вышки.'
python -X utf8 -m team_coach.control send hold_ultimate --target enigma_black_hole --bots 2 --ttl 6 --reason 'Союзники ещё подходят.'
python -X utf8 -m team_coach.control send bait --target 5 --bots 1 3 --ttl 26 --reason 'Выманить BKB и зайти после окончания.'
python -X utf8 -m team_coach.control cancel COMMAND_ID
```

Для `push` и `defend` параметр `--target` задаёт линию. Для `hold_ultimate` он задаёт имя способности. Для плана файта это ID противника из `fight_choices`. У `farm` и `retreat` цель — сам бот, `--target` опускается. `send` и `cancel` берут данные сессии у сервера. При нестандартном порте укажи `--port` перед подкомандой.

### HTTP-запросы

`POST /commands` принимает `session_id`, `clock_s`, `action`, `target`, `bot_ids`, `ttl_s` и `reason`. Возьми `session_id`, игровое время `context.clock_s` и ID союзников из свежего `GET /status` при `phase=active`. Сервер требует снимок давностью до 12 игровых секунд, от одного до трёх уникальных ID живых ботов и причину длиной 1–140 печатных символов. Срок задаётся целым числом в игровых секундах. Отсчёт идёт от переданного `clock_s`. Команда может завершиться раньше, если обстановка изменилась.

В PowerShell можно проверить состав и каталог до отправки.

```powershell
$coach = 'http://127.0.0.1:32125'
(Invoke-RestMethod "$coach/status").context.allies
(Invoke-RestMethod "$coach/commands").catalog.actions
```

Пример отправки `retreat` использует бота с ID 2. Подставь актуальный ID из состава.

```powershell
$match = Invoke-RestMethod "$coach/status"
if ($match.phase -ne 'active') { throw 'Тренер ещё ждёт игровые сводки.' }
$request = @{
    session_id = $match.session_id
    clock_s = $match.context.clock_s
    action = 'retreat'
    target = @{ kind = 'self' }
    bot_ids = @(2)
    ttl_s = 8
    reason = 'Бот принимает урон, союзники отходят.'
} | ConvertTo-Json -Depth 4
$command = Invoke-RestMethod "$coach/commands" -Method Post -ContentType 'application/json; charset=utf-8' -Body $request
$command
```

Чтобы отменить активную команду из примера, отправь её ID.

```powershell
$cancel = @{ session_id = $match.session_id; command_id = $command.id } | ConvertTo-Json
Invoke-RestMethod "$coach/commands" -Method Delete -ContentType 'application/json; charset=utf-8' -Body $cancel
```

`DELETE /commands` также отменяет план линии по его ID. Старый вход `POST /plan` принимает поля `objective` и `lane` вместо `action` и `target`. В нём `objective="hold"`, `lane="none"`, `bot_ids=[]` и `ttl_s=0` очищают план линии. `hold` в этом входе касается только плана, `hold_ultimate` действует на указанную способность.

Ответ о приёме содержит ID и время истечения команды. Смену режима или блокировку ультимейта проверяй по `applied` и `command_applied` в `GET /status`. Сбор сводок по журналу Dota подтверждён в живом матче лиги. Прямые запросы из Bot Lua к локальному HTTP-серверу в той проверке вернули статус `0`.

Сбор и фокус в планах файта проходят через роум Open Hyper AI. Интеграцию файловых ответов и фактический выбор этого режима движком ещё предстоит подтвердить в живой игре.

## Где править

1. **Добавить игровой сигнал.** Снимок собирается в `snapshot` и `mapSnapshot` в [adapter.lua](adapter.lua). Поля нормализуются в `_bot` и `_map` в [service.py](service.py). Локальный `POST /exchange` передаёт состояние и возвращает текущий план или `null`. Примерно раз в две игровые секунды `CoachService.observe()` пишет запись `observation`.
2. **Изменить правило наблюдения.** [shadow.py](shadow.py) сравнивает последовательные снимки в `ShadowObserver.update` и пишет через сервис записи `match_event`. Правила отмечают затянувшийся фарм при окне для пуша, разрозненный пуш, бой в изоляции или после потерь. Для ультимейтов разделяются наблюдаемая активность способности и начало её перезарядки. Окно между снимками оставляет короткие касты, цели и результат применения неопределёнными.
3. **Изменить решение по текущим командам.** [policy.py](policy.py) выбирает цель и участников среди допустимых вариантов из `_choices` в [service.py](service.py). `CoachService.review()` пересматривает решение каждые 15 игровых секунд или раньше при некоторых событиях. [strategist.py](strategist.py) поставляет дополнительную подсказку, которую местная политика проверяет по свежим данным.
4. **Добавить команду.** Описать действие и цель в `commands.py`, проверку живого состояния в `service.py`, чтение и исполнение в `adapter.lua` и хук нужного скрипта в `install.py`. Для коротких команд файта нужен отдельный срок действия и подтверждение эффекта от бота.

## Проверка и разбор матча

```powershell
python -m unittest discover -s tests -p test_team_coach.py -v
```

В **Local Host** с **Local Dev Script** рост `observations` в `GET /status` и записи `observation` в журнале подтверждают подключение и поток данных. В режиме `shadow` поле `plan` равно `null`. Для плана линии журнал пишет `plan_accepted` и `bot_applied`. Для остальных команд записи называются `command_accepted` и `command_applied`. Подтверждение означает фактическую смену режима после надбавки или срабатывание запрета перед постановкой ультимейта в очередь. Результат на карте проверяется по последующим снимкам.

Для разбора эпизода сопоставь игровое время, `mode`, исходные оценки из `desires`, состояние линии, видимых героев рядом и последующие события. [Инструкция отдельной сессии](observer-session.txt) задаёт формат записи в `review.md`.
